# FlipLedger

Reseller profit tracker plus cross-lister. It's a PWA for many unrelated resellers: each user signs up and only ever sees their own data. The client is Nick (repo `shdebaets/profittracker`). Production runs at https://profit.emoneydeals.com on Vercel (the old https://profittracker-iye3.vercel.app still works; keep it in the extension manifest), with Supabase via the Vercel Marketplace integration.

## Stack

- **Next.js 16.3** (App Router) and React 19. APIs differ from older Next; read `node_modules/next/dist/docs/` before writing routes, proxy or error code (see AGENTS.md).
  - `proxy.ts` replaces `middleware.ts`.
  - `error.tsx` and `global-error.tsx` get `retry()`.
  - Route handlers are typed with `RouteContext<"/path/[param]">`.
  - `route.ts` files may only export HTTP handlers and route config; put helpers in `lib/`.
- **Supabase:** Postgres with row-level security (RLS) on every table, no ORM, `@supabase/ssr`. Plus Storage (private `item-photos` bucket) and Auth (sessions; people sign in with Whop, see "Login and membership").
- **UI:** Tailwind v4, shadcn plus `@base-ui/react`, lucide icons, sonner toasts. Mobile-first: test at 375px.
- **Look:** from the client's Claude Design canvas. Fonts in `app/layout.tsx`: Inter (text), Space Grotesk (`h1`–`h3`, `font-heading`), JetBrains Mono (`font-mono`, for money). Colors are hex tokens in `app/globals.css`: the app is light (`:root`), the sign-in page uses the design's dark landing look (`.dark`). Brand orange `#f5982a`, profit green `#0e8f55`.
- **zod 4** for every server-action input. **vitest** for unit tests.

## Architecture

- **Mutations** are server actions in `app/(app)/actions/*.ts`. Each one: zod-parse → `requireUser()` → Supabase call → `revalidatePath("/", "layout")`. It returns `ActionResult`, and every catch goes through `fail(e)`.
- **Reads** are in `lib/data.ts` (server-only). `getItems()` also signs photo URLs and joins `marketplace_listings`.
- **Login and membership** (`lib/whop/`):
  - **Sign in with Whop** only in production. The Whop app's redirect URI is `https://profit.emoneydeals.com/auth/whop/callback` (plus `http://localhost:3000/auth/whop/callback`); the callback URL is built from the request's host, and `*.vercel.app` redirects to the custom domain first. `/auth/whop/start` → Whop OAuth (PKCE, state in a cookie) → `/auth/whop/callback`. The callback reads Whop `userinfo`, finds the Supabase user (`whop_links.whop_user_id`, else the *verified* Whop email, which is how email-login accounts kept their data, else a new user), and mints a normal Supabase session with `admin.generateLink({ type: "magiclink" })` + `verifyOtp`. Whop tokens aren't stored.
  - **What's paid:** all of FlipLedger, one plan (Nick, Nov 15 2026): the membership is Whop product `prod_N6zbl5IfKlk7g` (still called the Cross-Lister on Whop and in env var names). Without it, people are **view-only**: they can see and export their history (CSV, tax PDF, print report) but not add or change anything, and `MembershipBanner` shows on every page.
  - **Enforcement:** every server action that changes data calls `requireMember()` (throws a `UserError`, `MEMBERSHIP_LOCKED`). Account housekeeping stays on `requireUser()`: settings, tax bracket/form, push, signing photos, `disconnectEbay`, billing, and `endListing({ manual: true })` so lapsed members can clear delist alerts. New actions that write data must use `requireMember()`. Pages and the layout use `isMember()` to hide cross-listing tools behind `CrosslistUpsell`; `/crosslister` is the Membership page (buy, "I already bought it", billing). Access = email in `FLIPLEDGER_FREE_EMAILS`, or Whop `checkAccess` says yes (customer or admin) for any of `WHOP_CROSSLIST_PRODUCT_IDS`. The answer is cached 10 minutes in `whop_links` (service-role only, no RLS policies, so users can't grant themselves access); if Whop errors, the last answer stands.
  - **Kill switches:** empty `WHOP_CROSSLIST_PRODUCT_IDS` = everyone is a member. Empty `WHOP_CLIENT_ID` = email login comes back. `ALLOW_EMAIL_LOGIN=1` shows the email form for local QA. Set the product IDs only after `WHOP_CLIENT_ID`: users who never signed in with Whop have no `whop_links` row and can't be granted a membership.
  - The daily cron doesn't check access, so lapsed members' eBay sales still sync into their profit numbers.
  - **Linking an existing account:** if someone is already signed in (an older email-login account) when the Whop callback runs, `linkWhopToCurrentUser` attaches Whop to that account instead of matching by email, so a different Whop email can't make a second, empty account. `/crosslister` shows "Connect your Whop account" (`/auth/whop/start`) to signed-in users with no `whop_links` row. If someone signs in fresh with a Whop email that differs from their old FlipLedger email, they still get a new empty account; fix by pointing `whop_links.user_id` at the old user.
  - **Billing and the cancel flow** (`lib/whop/billing.ts`, `/crosslister`, `/crosslister/cancel`): reads the user's Cross-Lister memberships from Whop (`GET /memberships?user_id&product_ids&statuses`), shows plan and renewal date, and runs the cancel flow inside FlipLedger: their numbers for this calendar year (tax savings, miles, expenses, items bought), what stops (adding and editing, cross-listing, auto-delist, Smart Offers, AI listing) and what stays (viewing and exporting history), then save offers before a cancel at period end.
  - **Yearly banner** (`YearlyPlanBanner`, `showYearlyBanner`): October through March, monthly members who aren't paused see "Go yearly" on `/crosslister` and the dashboard, linking to `WHOP_CROSSLIST_ANNUAL_URL`. The dashboard's copy (`DashboardYearlyBanner`) streams in under Suspense because it waits on Whop, and skips the Whop call out of season. Offers: half price for 1–3 months instead of a free pause (Nick, Nov 15 2026; monthly members only, full access kept), applied with `/memberships/{id}/apply_promo_code` using one of three Whop promo codes in `WHOP_HALF_OFF_CODES` (50% off, `promo_duration_months` 1, 2 and 3, in that order; hidden unless all three are set), and the yearly plan (`WHOP_CROSSLIST_ANNUAL_URL`). Memberships paused before this still show Resume. Once a yearly membership is live, `billingState` sets any monthly one to cancel at period end. Actions never take a membership id from the browser; they look it up from `whop_links`. Plans on Whop (eMoney Inner Circle, `biz_nfZESqY1ozpUqF`): $30/month `plan_t4m0Uu4JBQbM0`, $300/year `plan_6PimZZjEnRdYN`, plus a free one. The FlipLedger Whop app is `app_aRVAnzNgupBdws`; `WHOP_API_KEY` is a business key on eMoney Inner Circle.
- **Money** is always stored as integer cents. Profit math lives in `lib/profit.ts`.
- **Items:** `status` is `inventory | sold | returned`. A partial sale splits the row (`lib/items/sell.ts`). "Listed" isn't a status; it's derived from active `marketplace_listings` rows.
  - `platform` is only a fee preset (several sites share one). Which marketplace it sold on is `sold_on`, written by every sale path through `recordSale`'s `soldOn`; null means in person, or an old sale that couldn't be backfilled.
  - `shipped_at` null on a sold item means it's still to ship. Manual sales without a marketplace count as handed over.
- **Orders** (`/orders`, `lib/orders.ts`, `getOrders()`): sold items joined to `marketplace_sales`, which now carries eBay's `buyer` (username only, never the address), `ship_by` and `order_status`. A partial eBay sale repoints its `marketplace_sales.item_id` to the new sold row. Poshmark and Mercari pages give no buyer or ship-by.
- **Photos:**
  - Up to 12 per item, compressed in the browser (`lib/image.ts`, 1600px JPEG).
  - Uploaded by direct PUT to signed upload URLs.
  - Stored at `item-photos/{user_id}/{uuid}.jpg`.
  - `photo_paths` is copied on partial sales, so delete files only with `removeUnreferencedPhotos`.
- **Errors:** `lib/errors.ts`.
  - Throw `UserError` for messages written for people.
  - Everything else is translated by `friendlyError()`: eBay, Supabase database/auth/storage, network, zod.
  - `fail()` and `reportError()` log the original. Never show raw `e.message` to users.
  - Crashed pages are handled by `app/(app)/error.tsx` and `app/global-error.tsx`.
- **Admin client:** `lib/supabase/admin.ts` uses the service role and bypasses RLS. It's only for cron, webhooks, the photo-link route, `marketplace_accounts` tokens and `marketplace_sales` writes (that table has no insert policy). Always scope by user yourself.

### Taxes

- `lib/tax.ts` (pure, tested) and the `/taxes` page. Every figure is an estimate; always show `TAX_DISCLAIMER`.
- **Tax bracket:** `settings.tax_bracket` (fraction, default 0.22) and `tax_bracket_set` (false until the seller picks one). While it's false, the `(app)` layout shows the first-run `TaxBracketOnboarding` sheet ("Skip" saves 22% and marks it set; swiping it away hides it for the browser session) and `TaxSavingsCard` keeps a picker too.
- **Tax savings** (dashboard and `/taxes`) = (COGS + mileage + expenses + subscriptions) × bracket for the calendar year.
- **Platform of a sale** (`salePlatform`): its sold cross-listing's marketplace, else the fee preset (`mercari_depop` counts as Mercari, `facebook` as Facebook, `cash` as local).
- **1099-K Reconciler:** marketplaces don't send us 1099-K numbers, so the seller types each form's gross into `tax_forms` (per year and platform). Expected 1099-K gross = logged gross + `items.sales_tax_cents` + `cancelled_sales`; anything left over is "on the 1099-K but not logged here". `gapBreakdown` walks the whole year from the IRS number to net profit (sales tax, cancelled, refunds, fees, labels, COGS, mileage, expenses, subscriptions).
  - **Sales tax** (`items.sales_tax_cents`): eBay sync fills it from `lineItems[].ebayCollectAndRemitTaxes`; other sales take an optional field in the sale form. It's never income or revenue.
  - **Refunds** (`items.refund_cents`, item detail → "Refunded the buyer?"): lowers that sale's net in `calcSale` (revenue stays gross) and fills Schedule C line 2. Not synced from eBay: `getOrders` only returns orders created since the last sync.
  - **Cancelled sales** (`cancelled_sales`): logged by hand on `/taxes` because Poshmark can still count them on the 1099-K. eBay cancellations aren't recorded (they don't count there).
- **Schedule C:** expense categories map to lines in `SCHEDULE_C_EXPENSE_LINES`; meals are halved; labels and subscriptions go to 27a.
- **Quarterly estimates** use IRS periods (Jan–Mar, Apr–May, Jun–Aug, Sep–Dec; Q4 due Jan 15) and `estimatedTax` = 15.3% SE tax on 92.35% of net + bracket × (net − half SE).
- **PDF:** "PDF report" on `/taxes` builds a real PDF in the browser with `pdf-lib` (`lib/tax-pdf.ts`, so tax years follow the seller's time zone) and shares or downloads it (`shareOrDownload` in `lib/csv.ts`; the installed iOS app can't download). Standard fonts only draw WinAnsi, so text goes through `pdfText`. `/tax-report/[year]` stays as a printable view.
- **Mileage log:** `expenses.start_location`/`end_location`. GPS trips save their first and last fix as "lat, lon"; manual trips take typed places.

### Lots, stale inventory, edit everywhere

- **Lots** are `hauls` (`lib/lots.ts`, `/lots`, `HaulForm`). `/lots?lot=<id>` opens one lot (the item sheet links there from `haul_id`). `updateHaul` edits name, store, date and receipt (items still carrying the lot's old store/date follow; receipts upload through `lib/receipt-upload.ts`); `deleteHaul` deletes the lot and its receipt file, and the FK's `on delete set null` keeps its items. Split mode `even` (same cost per unit) or `value` (by estimated resale value, `distributeHaul`), optional receipt photo (`hauls.receipt_path`, same `item-photos` bucket, path must start with the user's id). Items keep `haul_id`, also on partial-sale rows, so `lotStats` can show what a lot returned: sale revenue minus fees and labels, before the lot's cost; ROI = (returned − lot cost) / lot cost.
- **Stale alerts** (`lib/stale.ts`): an inventory item is stale after `settings.stale_days` (30/45/60/90/120, default 60) counted from its first live listing, else its purchase date. Dashboard card → `/inventory?filter=stale`.
- **Bulk reprice** (`RepricePanel`, `components/reprice-panel.tsx`): one panel for "Select to reprice" multi-select on `/inventory`, the stale filter and the overpriced results. Modes: Suggested (each item's 90-day sold median, `soldMedians` in `lib/sold-medians.ts`, worked out on the server), drop %, drop $, set price. `planReprice` (`lib/reprice.ts`, pure, tested) is shared by the preview and `repriceItems`: never below $0.99, from `askingPrice` = list price else highest live listing price, items already at the price are left alone.
- **Edit once, update everywhere** (`lib/crosslist/edit.ts`): `saveListingDetails` and `repriceItems` call `propagateToListings` with what changed. eBay is revised in place (`lib/marketplaces/ebay/revise.ts`: `bulk_update_price_quantity` for price/quantity, which answers 200 even when a line fails so check `responses[]`; title/description by GET + PUT of the inventory item, dropping read-only fields, plus the offer's `listingDescription`). Assisted sites get `marketplace_listings.sync_status = 'pending'` with `pending_changes`; failures get `failed` + `sync_error` and a Retry (`retryListingSync` passes `listingId` so only that listing is re-sent). The crosslist panel's `SyncNotice` shows each listing's state; Inventory has a "Needs Update" chip (`?filter=sync`) and badges show ↻ for live listings that are pending or failed. `updateItem` also sends title, description (edit form's Listing Description box on stock), quantity and photo changes (`photoPaths`; eBay gets new `imageUrls` as short photo links on `APP_URL`). On assisted sites with extension 0.9.0+ (`extensionCanEdit`), "Update <site>" starts an `EDIT` job: the extension opens the listing, clicks its Edit button (only opens the form), fills the changed title/description/price, plus (0.11.0+) quantity where the form has a quantity box (`site.edit.fields.quantity`: Poshmark, Facebook; Mercari stays "your turn") and changed photos, which the form can only add, so the seller removes the old ones (`site.edit.photos`, photos sent as `photoUrls`). The seller saves; `EDITED` marks it synced. Not yet run on the real sites.
- **Overpriced alerts** (`lib/comps/overpriced.ts`, `findOverpriced`, `OverpricedCheck` on Inventory): items whose asking price is 25%+ above the 90-day sold median on file for their title (`comp_sales`, at least 3 sales, best offers left out). Results are ticked by default and repriced through `RepricePanel` (Suggested mode). The daily `/api/cron/alerts` reads sold prices for products with live listings that nobody comped in 7 days (`lib/alerts/prefetch-comps.ts`, never-read first, `OVERPRICED_PREFETCH_LIMIT` products a run, default 10, and at most half the provider's daily requests) through `refreshSoldFromApi`, so overpriced checks have data.

### Scan to Comp (CompAmp in FlipLedger)

- `/comp` (bottom-bar "Comp" tab, which it shares with `/calculator` via `CompCalcTabs`; also the header scan button): camera barcode scan (`BarcodeDetector` on Android Chrome, ZXing `@zxing/browser` on iPhone), a photo, or typed UPC/keywords → `lookupComps` (`lib/comps/`).
- **Photo scan** (`lib/comps/photo.ts`, `compPhotoIdentify`): the "Photo" button takes or picks a picture, the browser shrinks it to a 1024px JPEG (sent as a data URL, under the 1MB action cap), and Claude (`AI_MODEL`, forced tool call, same setup as `lib/ai/listing.ts`) returns the product, a search phrase and any readable barcode. The page then runs the normal lookup on the barcode or the phrase, so the "Which one is it?" picker still applies. Capped per user at `COMP_PHOTO_DAILY_LIMIT` (default 40) a day, logged in `ai_usage` as `comp_photo`.
- **Profit box** (`lib/comps/profit.ts`, tested): platform picker built from the registry's marketplaces and their fee presets (eBay 13.25%, Mercari/Depop 10%, Poshmark 15%, Facebook/Vinted 0%) plus an editable shipping label (default $6). The sale price is always the eBay estimate. Platform, shipping and the last store are remembered per device in `localStorage` (`fl:comp:platform`, `fl:comp:ship`, `fl:lastStore`).
- **"I bought it"** opens the add form in inventory mode with title, shelf price, store and the estimate as "Expected sale price" (saved as `items.list_price_cents` via `createItem`'s `listPriceCents`). **Save now** inserts the same inventory item in one tap.
- **Days of supply, not days to sell:** OpenWeb Ninja's sold results are eBay search cards (sold date, price, shipping, location, format) with no listing start date or duration, so a real average time-to-sell can't be worked out. The stat is `daysOfSupply` (live count ÷ the 30-day sales pace), labelled "days of supply" with a one-line explanation. The provider's field names are logged as `[sold data] fields` on each paid read; if a start date ever shows up, compute it there.
- **Live listings:** eBay Browse API `item_summary/search` by `gtin` or `q` with the app token (`getAppToken`, cached per server instance), no seller login, 100 listings per call. eBay's public APIs don't give sold prices (Marketplace Insights needs eBay approval).
- **In the Profit Calculator:** `CompFill` (scan or type, pick the product) puts the eBay estimate into Sale Price and switches fees to eBay.
- **API budget:** Browse is 5,000 calls a day for the whole app by default. Every search goes through `comp_cache` (`lib/comps/cache.ts`, service role only, shared): live results for 2 hours, so a product costs at most one call per 2 hours however many people scan it or refresh it. Tracked products refresh only on tap (no cron).
- **Which product?** (`lib/comps/identify.ts`, from CompAmp's `identify`): typed words like "pokemon upc" cover many products, so Claude groups the live listings into up to 6 distinct products (cached a day per search) and the seller picks one (`CompPick` → "Which one is it?"). Comps are then searched and judged for that exact product. Barcodes skip the picker: the product is the top product identify finds in the barcode's listings (cached a day), else its first listing title. `tracked_products.product` keeps the pick for refreshes.
- **Sold prices:** since 22 July 2026 eBay only shows sold/completed searches to signed-in members, so server scraping and most data vendors (SerpApi deprecated its Sold filter in Sept 2026) can't get them. The extension works because it runs in the seller's own signed-in Chrome; if they're signed out the comps tab lands on eBay's sign-in page and the app times out with a sign-in hint. The official route is the Limited Release Marketplace Insights API (apply via an eBay "Application Growth Check" ticket).
- **Sold prices:** `comp_sales`, shared by all users (public market data; read policy for authenticated, writes only through `saveSoldComps` with the service role). Rows are filed under `queryKey(query)`, where query = `searchPhrase(product)`.
- **Browser reads are OFF** (`BROWSER_SOLD_READS = false` in `lib/sold-browser.ts`, Nov 14 2026): Nick wants every member on one source, the paid provider, because mixing reads made counts jump. Everything below about the extension/phone app reading sold prices is dormant until that flag is flipped; the extension nudge on `/comp` is hidden too.
- **Browser first, paid last** (`lib/sold-browser.ts`, dormant): `soldSource` picks where sold prices come from on this device: the Chrome extension (0.8.0+; 0.10.0 sends the `soldPhrase` words, US sellers only `LH_PrefLoc=1`, newest first, and eBay's result count), else the phone app's eBay window (`lib/native-ebay.ts`, `mobile/`), else nothing. With a source, `compLookup(q, product, true)` skips the paid provider, and `/comp` and `CompFill` read eBay themselves when the sold data is missing or over 12 hours old (`pullSoldHere` → `saveSoldComps(query, rows, total)`). That's one eBay page (up to 240 sales) per search, up to 3 searches, per product per 12 hours, shared with everyone. `saveSoldComps` stamps the rows and writes the same `comp_cache` `sold8:` marker the paid provider uses (`requests: 0`), so the server won't pay for that search for 12 hours and the stats can use the read and its eBay total. If eBay blocks the read (signed out, captcha), the lookup runs again with the paid provider. The page parser is `collectSoldPage` (`lib/comps/collect-sold.ts`, self-contained because the phone app injects it with `toString`); `extension/comps-ebay.js` has the same rules and a test checks both give the same rows. We count sales records, not units: a multi-quantity listing counts once (CompAmp opens each listing to count units; we don't, to keep it to one page per lookup).
- **Sold prices from the server** (`lib/comps/sold-api.ts`): with `SOLD_DATA_API_KEY` (OpenWeb Ninja Real-Time eBay Data API, `GET https://api.openwebninja.com/real-time-ebay-data/search?query&show_only=sold_items&domain=com&page`, header `x-api-key`, 60 results a page), `lookupComps` reads sold listings (newest first, `sort_by=RECENTLY_SOLD`, paging while a full page is still inside 30 days, up to `SOLD_DATA_MAX_PAGES` default 4) into `comp_sales` when that search wasn't read in the last 12 hours (`comp_cache` key `sold3:<queryKey>`, written only after the rows are saved; rows are de-duplicated by `external_id` because pages overlap; the daily cap counts requests), so phones get sold prices without the extension. Capped at `SOLD_DATA_DAILY_LIMIT` requests a day (default 300). The parser (`toSoldRow`) is tolerant because the provider's field names aren't fully documented; the first result's field names are logged as `[sold data] fields`. Best-offer sales show the asking price there too, and without a seller cookie the provider can't flag them, so they count at the asking price. The comp screen lists the sales behind the price (`recentSales`) and the ones the judge dropped (`droppedSales`) so sellers can check. Never throws: comps fall back to live listings.
- **Stats** (`lib/comps/stats.ts`, from CompAmp's sold research): 30/90-day sold medians (price + shipping via `landed`; sales with shipping over $25 are overseas sellers with converted, inflated prices, so they're left out of prices but still counted; best offers left out), live count and lowest Buy It Now (ignoring anything under 60% of the live median), sell-through = sold30 / (sold30 + live), days of supply. Estimate = median of the newest 20 sales (after dropping prices over 1.3x their median, mostly best offers showing the asking price) when there are 8+ sales in the last 7 days (`estimateSource: "recent"`, busy products move fast), else sold 30d median, else 90d, else live median. When the latest sold read (rows sharing its `collected_at`) spans under 25 days at its 90th-percentile age and has 20+ sales, `sold30` is worked out from that pace (`soldPace`, `sold30Estimated`, shown as "~N sold 30d (pace)"), capped at eBay's result count scaled by the judge's keep share (`lastSoldRead`). When the read already holds 90%+ of eBay's count (a slow product: every sale was read), there's no projection: the count is the count. The sold search uses `soldPhrase` (product name minus TCG/Celebration/Anniversary/edition and parentheses) because eBay needs every word to match; the judge drops the extra look-alikes. Live count is eBay's `total` for the search scaled by the share the judge kept (not just the 100 read). New vs used/open-box estimates (`newEstimate`/`usedEstimate`) show once there are 3+ prices of each. Profit = estimate − 13.25% eBay fee − $6 label − cost.
- **Several searches per product** (`lib/comps/variants.ts`): eBay needs every word to match, so one phrase misses sales titled differently. `searchVariants` asks a small Claude model for 2 or 3 short searches worded the way different sellers title the product (from its live titles), merged with `soldPhrase` by `mergeSearches` (max 3, cached a week per product as `var:<queryKey>`). `lookupComps` returns them as `searches`; the paid provider reads the first one deep (up to `SOLD_DATA_MAX_PAGES`) and the others one page each, and the extension/phone app read one eBay page per search. Rows are merged by listing id under the product's `queryKey`, eBay's count is the biggest of the searches', and the AI judge drops the look-alikes. The `comp_cache` read marker is `sold8:<queryKey>`.
- **Overseas sellers and the exact 30-day count:** the provider gives each sold item's `location`; `isOverseas` marks non-US items (`comp_sales.overseas`, migration 0020) and `landed` leaves them out of prices (converted, often VAT-inflated) while they still count as sales. When eBay's count for the first search runs past the pages read and those pages are all inside 30 days, the provider finds where eBay's results cross 30 days ago: it reads eBay's last page, then binary-searches up to 4 pages (5 extra requests at most, only for busy products), and saves `within30` (eBay results inside 30 days: whole pages + half the crossing page) in the read marker. `lookupComps` scales it by the judge's keep share of the read's last-30-day sales and `compStats` uses it as `sold30` (spreading eBay's 90-day total failed: launch items have presales and junk going back months). Without it, the pace estimate applies. Provider docs: with an eBay session `cookie` param best-offer sales come back as `buying_format: best_offer_accepted` (not used: it would need a member's eBay cookie on the server).
- **More detail** (`CompDetails`, `lib/comps/history.ts`): a fold-out under the numbers with 7D/30D/90D charts: price (sold median per day and lowest live), sales per day, live listings. Sold history is built from `comp_sales`; live history from `comp_snapshots` (one row per product per 2 hours at most, written by `lookupComps` with the service role), so live charts fill in as products get looked up. Plain SVG, no chart library.
- **Extension nudge:** on a computer (`pointer: fine`) without a sold-reading extension, `/comp` shows "Add (or Update) the FlipLedger Chrome extension" linking to `EXTENSION_STORE_URL`.
- **Tracked products** (`tracked_products`, per user): CompAmp's product tracking with a target cost. Refreshed on tap, and daily by the `sync-sales` cron (`refreshTrackedProducts`, `lib/comps/tracked-refresh.ts`): products not checked in 20 hours, oldest first, at most `TRACKED_REFRESH_PER_USER` (10) per user and `TRACKED_REFRESH_DAILY` (100) per run, and only while the paid sold-data requests in the last 24 hours are under `TRACKED_REFRESH_BUDGET_SHARE` (0.5) of `SOLD_DATA_DAILY_LIMIT`, so live scans keep the rest. It stops 250 s into the cron. Each refresh is a normal `lookupComps`, so it also writes a `comp_snapshots` row (which now keeps `sold_median_cents` and `sold30` too). **Alerts** (`lib/comps/tracked-alerts.ts`, tested; copy in `lib/push/comp-messages.ts`): web push when the sold median (30-day, else 90-day) crosses under the target buy price (once per crossing, judged against the previous check), or moves more than 15% from `alert_median_cents` (the median at the last alert or first check, so slow slides add up). With the extension on the computer, `/comp` reads sold listings by itself when there are none or they are over 12 hours old (once per product per visit).
- **AI judge** (`lib/comps/judge.ts`, from CompAmp's `judge`): before the stats, a small Claude model (`AI_MODEL`, forced tool call) keeps only listings that are the exact product (drops cases, lots, parts, empty boxes, other models). The product is the barcode's first live title or the picked product. The prompt treats other designs/prints/characters/colorways in the same line as different products and multi-design or multi-pack titles as rejects, while wording differences ("Royal Plush" vs "Plush") are the same item. `obviousMulti` also rejects counts ("x3", "set of 2", "all 3", not sizes like "50 x 60") and two products joined with " & " or " + ". Verdicts are cached per product + title hash (salted `v2|`; bump it when the prompt changes) in `comp_judgments` (service role only), so each title is judged once for everyone; spend is logged in `ai_usage` as `comp_judge`. If Claude is unavailable everything counts as kept. `lookupComps` returns `filteredOut`, shown under the estimate. `findOverpriced` uses the same judge.
- Not ported from CompAmp: version/edition pickers inside a product, the human review queue, collector leases and daily background refreshes. CompAmp itself (Lovable project `a7f2033a-…`, comp.emoneydeals.com) still runs separately.

### Smart Offers

- Rules in `smart_offer_rules` (Settings, Cross-Lister): start discount, max discount, floor = cost × (1 + margin), minimum listing age, how often. `offerPrice` (`lib/offers.ts`, tested) deepens the discount 1 point per week past the minimum age, never below the floor, and skips anything under 5% / $1 off.
- `runSmartOffers` (`lib/marketplaces/ebay/offers.ts`) runs from the daily `sync-sales` cron after each account's sale sync, only for sellers with Cross-Lister access (`hasCrosslistAccess`; lapsed members' sales still sync, their offers stop): Negotiation API `find_eligible_items` → for listings FlipLedger knows (so cost is known) `send_offer_to_interested_buyers`, 2-day offers, no counter-offers. "How often" is per listing (`offerDue` + `lastSentByListing` in `lib/offers.ts`, 1 hour of cron slack), for eBay and assisted alike. Each offer is logged in `smart_offers`.
- **Outcomes are real sales** (`lib/offers-settle.ts`, pure and tested; `settleAllOffers` in `lib/offers-settle-run.ts`), settled in their own cron step for every seller, eBay-connected or not. An offer is credited with a `marketplace_sales` line for the same seller and item (assisted sites: also the same listing, since their line id is our listing id), sold within 3 days of the offer at a unit price ≤ offer + $1; each sale goes to one offer (the latest before it; unique index on `smart_offers (sale_marketplace, sale_line_id)`). The offer stores `sale_line_id`, `sale_cents` (what the buyer paid × quantity) and `sold_at`. No sale 4 days after sending → `expired`. `marketplace_sales` now stores `sale_cents` (per unit), `quantity`, `sold_at` (eBay sync and assisted `claimSale`); older rows fall back to the sold item row. Items marked sold by hand have no sale line, so they don't credit an offer.
- **Offers report** in Settings (`offerReport`): sent, sold (share of settled offers) and revenue (sum of real `sale_cents`).
- **Poshmark and Mercari** are assisted, never automatic (no API; their terms ban bots): `getAssistedOffers` (`lib/offers-assisted.ts`, tested) lists active listings due an offer under the same rules, and Settings shows them. With extension 0.9.0+ "Fill offer" starts an `OFFER` job: the extension opens the listing, clicks its offer-to-likers button (opens the form only) and fills the price (`site.offer` in `site-*.js`); the seller sends it and clicks "I sent it" → `OFFERED` → `logAssistedOffer`, called by `ExtensionBridge` on any page (one log per listing per 10 minutes, since several tabs can hear the report). `smart_offers.marketplace` tells them apart. Selectors not yet run on the real sites.
- **Facebook Marketplace is left out**: it has no offer-to-likers feature, so there's nothing to fill.

### Cross-listing

- **Registry:** `lib/marketplaces/registry.ts` lists each marketplace's mode (`api` / `assisted`), sell URL, fee preset and photo limit.
- **Engine:** `lib/crosslist/engine.ts` (pure, tested with a fake store). When an item sells anywhere it ends API listings and marks assisted ones `delist_pending`. A partial sale only updates quantity. Failed ends become `error` with a friendly `last_error`. It's wired to Supabase in `lib/crosslist/store.ts`.
- **eBay:** `lib/marketplaces/ebay/`.
  - **One eBay developer app** (the client's), and **each user connects their own seller account** via OAuth.
  - Tokens are AES-GCM encrypted (`lib/crypto.ts`, `TOKEN_ENCRYPTION_KEY`) in `marketplace_accounts`. That table has no RLS policies; clients read the `marketplace_connections` view.
  - Publishing: Inventory API `inventory_item` → `offer` → `publish`. SKU = item id.
  - Sales: Fulfillment `getOrders`, synced on app open (`AutoSync`, at most every 5 minutes), via "Sync now", and by a daily cron at `/api/cron/sync-sales`. `marketplace_sales` makes it idempotent. `fetchOrders` only returns an order once (by creation date), so `refreshShipping` re-reads unshipped eBay orders from the last 60 days by ID and sets `shipped_at` when eBay says `FULFILLED`.
  - A line whose SKU isn't one of the seller's item ids (listed straight on eBay, or the seller's own SKU) becomes a new sold item with `cost_unknown = true` (`ebaySoldItem` in `lib/sales/untracked.ts`): title, quantity, price, buyer shipping and eBay's real fee from the order, no ad fee. Only orders since the account connected are read, so older sales don't come in.
  - `/api/marketplaces/ebay/account-deletion` is required by eBay for production keys.
  - **Business policies** (shipping, payment, returns) are required to list. Settings can create starter ones through the Account API (`createEbayPolicies` → `createPolicies`, `sell.account` scope) named "FlipLedger shipping/payment/returns", or link to eBay's page (`businessPoliciesUrl`). They're normal policies the seller can edit on eBay. USPS Ground Advantage's service code is `USPSParcel`.
  - **Promoted Listings** (cost per sale, `lib/marketplaces/ebay/promote.ts`, `sell.marketing` scope): each seller gets one manual campaign named "FlipLedger promoted listings" (id saved in `settings.campaignId`), and each listing is added by listing ID at its own rate (`bulk_create_ads_by_listing_id`, falling back to `bulk_update_ads_bid_by_listing_id` if it's already in there). Rates are 2.0–100.0 with one decimal (`normalizeAdRate`). The default (`settings.promote`) is set in Settings, and the List on eBay form and live eBay listings can override it. The rate is saved in `marketplace_listings.ad_rate`. A failed promotion never undoes the listing; it comes back as `promoteError`. Sale sync adds an *estimated* ad fee (`adFeeCents`: rate × item price plus shipping) because the order's `totalMarketplaceFee` doesn't include it. eBay only charges when the sale came through the ad, and it also counts tax.
- **Importing existing listings** (Settings → Import listings): Poshmark is read on the server from the public closet (`lib/import/poshmark.ts`, from the page's `__INITIAL_STATE__`, 48 a page via `max_id`); Mercari by the extension (servers get Cloudflare's challenge). `lib/import/plan.ts` skips listings already tracked, adds a listing to an inventory item with the same title (how one item gets both its Posh and Mercari listings), and creates the rest as items with `cost_unknown = true` (shown as "Add cost" / Needs Cost until the seller enters a cost). The client sends candidates in batches of 50 because server actions cap bodies at 1MB. Closets are ordered by last share, so a listing shared mid-read can be missed; importing again picks it up.
- **Photos to eBay** go as short signed links, `/api/p/<exp>/<sig>/<path>` (`lib/photo-links.ts`), because eBay rejects picture URLs over 500 characters (3,975 total).
- **Chrome extension:** `extension/` (MV3, plain JS, excluded from tsconfig). It auto-fills Facebook Marketplace, Poshmark and Mercari, including a category guessed from the title (`guessCategory`/`categoryPath` in `shared.js`, unit-tested; per-site menu texts are best guesses until run on the real sites). The user finishes what it can't and clicks Publish, unless they turned on auto-publish (per computer, like auto-delist; flags in `lib/extension.ts`). `runner.js` holds the flow and each site is a config in `site-*.js` (fields found by visible label or placeholder). The app talks to it via `window.postMessage` (`lib/extension.ts`, `components/crosslist/extension-bridge.tsx`). `registry.ts` marks which sites it supports (`extension`, `saleCheck`). None of the sites' selectors have been run on the real sites yet. Chrome Web Store: public, linked in the app via `EXTENSION_STORE_URL` (`lib/marketplaces/registry.ts`); the seller guide is the public `/extension` page. `npm run pack:extension` builds `dist/flipledger-extension-<version>.zip` (drops tests, docs and the localhost entries from the manifest); `extension/STORE.md` has the listing text, permission justifications and privacy answers, and the store links to the public `/privacy` page. Bump the manifest version for every upload. Request only permissions the code uses: the store rejected 0.6.0 for an unused `tabs` (only needed to read a tab's URL or title; creating, messaging and closing tabs work without it).
- **Auto-delist:** opt-in per computer (`localStorage`, Settings), off by default. `AutoSync` sends up to 3 `delist_pending` listings per tick, each tried once per page load. `runner.js` `autoDelist` only clicks on a page whose path contains the listing's ID (`FL.listingId`); any surprise reports an error and leaves the listing on the delist list. Buttons are per-site in `site-*.js` (`delist.auto`). Not yet run on the real sites.
- **Poshmark/Mercari sales:** read from each listing's public page by `saleStatus` (`lib/marketplaces/sale-status.ts`; the same rules are in `extension/shared.js`, and a test runs both on the same pages). Never use schema.org availability for this: a sold Poshmark listing says `OutOfStock` (same as not for sale) and a sold Mercari item says `InStock`. Read the listing's own field, matched by listing ID, because pages also carry similar items: Poshmark `inventory.status` (`sold_out`), Mercari item `status` (`trading`).
  - **Poshmark** runs on the server (`lib/marketplaces/assisted-sync.ts`) from `syncSales` on app open and from the daily cron, so it works on phones. `checked_at` throttles it. It only ever fetches `poshmark.com` (`poshmarkUrl`), because links are typed by users. A `poshmark check:` log line counts blocked pages.

  - `lib/crosslist/assisted-sales.ts` records the sale (one unit, fee from the marketplace's preset, price = page price) and confirms `delist_pending` listings that are gone. Idempotent via `marketplace_sales` (`external_line_id` = listing id). Needs the listing's URL.

## eBay gotchas (each one bit us)

- **`Accept-Language`:** Node `fetch` sends `Accept-Language: *` by default and eBay rejects it. `ebayFetch` sets `en-US`, so keep that on any new eBay call.
- **Condition:** allowed conditions differ by category. Load them with the Metadata API `getItemConditionPolicies` and send a condition ID that category allows (`EBAY_CONDITION_ENUM`, matching eBay's official table). Never hard-code one condition.
- **Item specifics:** required ones must be filled; the List button stays disabled until they are.
- **Keys must match the environment:** sandbox and production keys must never be mixed. `EBAY_ENV`, `EBAY_CLIENT_ID` (`SBX` vs `PRD`), `EBAY_CLIENT_SECRET` and `EBAY_RUNAME` must all come from the same keyset. Each keyset has its own RuName, and a mismatch shows up as `unauthorized_client` or a vague `temporarily_unavailable`.
- **Sandbox logins:** the sandbox only accepts sandbox test users, not real eBay accounts.
- **Seller setup:** "need some additional information to create a seller's account" means the user must finish seller setup on ebay.com. It isn't a field in our form.
- **Adding OAuth scopes:** a refresh may only ask for scopes the seller already granted, or eBay rejects it and the connection looks expired. Granted scopes are saved in `marketplace_accounts.scopes` (null means `LEGACY_EBAY_SCOPES`), refreshes use them, and features that need a new scope check for it (e.g. `canPromote`) and ask the seller to reconnect. Reconnecting the same eBay account keeps its settings (callback route).

## Git workflow

- **Start every session from the latest `main`:** run `git fetch origin` first and branch from `origin/main`. This checkout is often many commits behind.
- **Work in your own git worktree for every task**, never in the shared checkout or on a branch another session has checked out, so changes don't get mixed up: `git worktree add ../profit-tracking-app-<task> -b <branch> origin/main`. Other Claude sessions often share this folder, and uncommitted changes there are usually someone else's work in progress, so leave them alone. Symlink `node_modules` into the worktree; Turbopack builds fail through the symlink, so rely on the Vercel preview build (or run `npm ci` in the worktree and use `next dev --webpack`; Turbopack's `next/font` fails in a worktree even with its own `node_modules`).
- Work on a branch, open a PR to `main`, and let the user merge. Auto mode won't merge unreviewed PRs.
- **Before pushing more commits to a PR branch, check the PR isn't already merged.** Commits pushed after a merge never reach `main`; that happened once with PR #7.
- **Run tests before `git push`**, chained with `&&`, never `;`.
- `feature/google-signin` holds a finished Google sign-in. Keep it off `main` until the client asks.
